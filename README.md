# Google Indexing Manager

Плагин WordPress для работы с индексом Google: собирает URL сайта, проверяет,
проиндексированы ли они, и отправляет не проиндексированные страницы на
повторный обход через Google Indexing API. Отправка идёт в фоне через WP-Cron,
в ночном окне, с учётом суточных квот Google. Ключ сервисного аккаунта хранится
в базе в зашифрованном виде.

Версия 1.12.2. Требуется WordPress 7.0+ (проверено до 7.1) и PHP 8.4+.

## Как это работает

1. **Синхронизация** собирает URL опубликованных записей и страниц (типы
   контента выбираются в настройках) и складывает их в таблицу очереди.
2. **Проверка** по одному URL спрашивает у Search Console (URL Inspection API),
   проиндексирована ли страница, и сохраняет статус и состояние покрытия.
3. **Отправка** передаёт не проиндексированные URL в Indexing API
   (`URL_UPDATED`), после чего отмечает дату отправки.
4. **Перепроверка** возвращается к страницам, которые так и не попали в индекс,
   через заданное число дней, и повторно отправляет их через другой порог.

Всё это делает WP-Cron: отдельные цепочки для синхронизации, проверки,
отправки, статистики и очистки логов. Здоровье цепочек раз в 15 минут
восстанавливает healthcheck, поэтому после сбоя хостинга ничего не «зависает».

## Требования

- WordPress 7.0 или новее (проверено до 7.1), PHP 8.4 или новее.
- Проект в Google Cloud с включёнными **Indexing API** и **Google Search Console
  API**.
- Сервисный аккаунт с JSON-ключом и доступом к ресурсу в Search Console.
- Рабочий WP-Cron (или системный cron, дергающий `wp-cron.php`): на сайтах с
  нулевым трафиком фоновые задачи без него не запускаются.

## Установка

1. Скопировать каталог `google-indexing-manager` в `wp-content/plugins/`.
   Можно и просто установить zip-архив через «Плагины» → «Добавить новый».
2. Активировать плагин.
3. Открыть «Настройки» → «Google Indexing» и выполнить три шага из блока
   «Как подключить» на вкладке «Настройки» (они же ниже).
4. Нажать «Синхронизировать URL» на вкладке «Статистика» или дождаться
   ночной синхронизации.

## Подключение сервисного аккаунта

Порядок одинаков для интерфейса и для этого раздела.

### 1. Google Cloud: сервисный аккаунт и JSON-ключ

1. Создайте проект в [Google Cloud](https://console.cloud.google.com/).
2. Включите в нём **Indexing API** — именно её плагин использует для отправки.
   Для проверки статуса включите также **Google Search Console API**
   (URL Inspection API работает только с ним).
3. Создайте сервисный аккаунт (роли в проекте ему не нужны) и выпустите для
   него ключ в формате **JSON**. Файл скачивается один раз, сохраните его.

Официальная инструкция: [Indexing API — предварительные требования](https://developers.google.com/search/apis/indexing-api/v3/prereqs).

### 2. Search Console: доступ для сервисного аккаунта

1. Откройте [пользователей Search Console](https://search.google.com/search-console/users)
   для нужного ресурса.
2. Добавьте `client_email` из JSON-файла (вида
   `name@project.iam.gserviceaccount.com`) с правами **«Владелец»** или
   **«Полный доступ»**. Прав «Ограниченный доступ» недостаточно: API вернёт 403.

### 3. Плагин: вставить JSON и проверить

1. Вставьте содержимое JSON-файла целиком в поле «JSON-ключ сервисного
   аккаунта» и сохраните настройки. Поле всегда пустое: сохранённый ключ не
   отображается, показываются только маска, `client_email` и дата сохранения.
2. Укажите «URL сайта в Search Console»: для ресурса-домена это
   `sc-domain:example.com`, для ресурса-префикса — `https://example.com/`
   (со слэшем в конце). Значение должно совпадать с Search Console.
3. Откройте вкладку «Диагностика» и нажмите «Запустить диагностику»: она
   проверит ключ, токен, список ресурсов, права, URL Inspection API и Indexing
   API.

Если ключ нужно заменить, вставьте новый JSON и сохраните. Если удалить —
кнопка «Удалить JSON-ключ» в разделе «Обслуживание»: действие явное, пустое
сохранение настроек ключ не стирает.

## Шифрование ключа

JSON сервисного аккаунта содержит `private_key`, которым подписываются запросы
к Google. Ключ действует, пока его не отозвали в Google Cloud, поэтому плагин
хранит JSON не открытым текстом, а шифротекстом (AEAD: XChaCha20-Poly1305,
SecretBox или AES-256-GCM — что доступно в PHP). Дамп базы без `wp-config.php`
тогда бесполезен.

Ключ шифрования берётся так:

1. константа `GIM_KEY_ENCRYPTION_KEY` в `wp-config.php` — base64 от 32 байт;
2. иначе — ключ, выведенный через HKDF-SHA256 из солей WordPress
   (`AUTH_KEY`, `SECURE_AUTH_KEY`, `LOGGED_IN_KEY`, `NONCE_SALT`);
3. иначе — сохранение ключа запрещено (fail closed), плагин продолжает
   работать с тем, что уже сохранено.

Сгенерировать константу:

```bash
php -r "echo base64_encode(random_bytes(32));"
```

и добавить в `wp-config.php` до строки «That’s all, stop editing!»:

```php
define( 'GIM_KEY_ENCRYPTION_KEY', 'вставьте-сюда-строку-base64' );
```

Что важно знать:

- **Смена солей.** Без константы ключ шифрования зависит от солей: если соли
  сменить, шифротекст перестанет расшифровываться. Плагин покажет «Ключ не
  читается» и попросит вставить JSON заново. С константой ключ от солей не
  зависит.
- **Константу нельзя менять** после сохранения ключа: старый шифротекст станет
  нечитаемым, JSON придётся вставить заново.
- **Потеря ключа шифрования не отзывает ключ в Google Cloud.** Если JSON мог
  попасть в чужие руки, удалите ключ сервисного аккаунта в Google Cloud,
  выпустите новый и вставьте его в плагин.
- Ключ не попадает ни в HTML, ни в JavaScript, ни в лог, ни в диагностику:
  в интерфейсе только маска и `client_email` (он не секрет).
- OAuth access token (`ya29.…`), который плагин получает на час, тоже хранится
  зашифрованным: тем же ключом, но со своей привязкой (AAD
  `gim|access_token|v1|gim_access_token`). Рядом лежит только срок действия —
  обычное число, не секрет. Если шифротекст не читается, плагин считает, что
  токена нет, и запрашивает новый.

## Настройки

«Настройки» → «Google Indexing», вкладка «Настройки» (право `manage_options`):

- **JSON-ключ сервисного аккаунта** — вставка ключа, маска сохранённого ключа,
  удаление отдельной кнопкой.
- **URL сайта в Search Console** — ресурс, с которым сверяются проверки.
- **Типы контента** — какие публичные типы записей собирать (по умолчанию
  записи и страницы). Применяется со следующей синхронизации.
- **Ночное окно отправки** — интервал, в котором разрешена отправка (по
  умолчанию 22:00–06:00, окно может пересекать полночь).
- **Суточный лимит отправок** — локальный предохранитель, 1–200, по умолчанию
  100: часть квоты Google может расходоваться другими инструментами.
- **Перепроверка и переотправка** — через сколько дней снова проверять статус
  (по умолчанию 14) и повторно отправлять (по умолчанию 30).
- **Срок хранения логов** — 0 означает «хранить бессрочно»; иначе старые записи
  удаляются раз в сутки.
- **Исключающие теги** — записи с этими тегами не отправляются (но
  проверяются).

Раздел «Обслуживание»: сброс access token, сброс статусов проверок, пересчёт
исключений, очистка логов и удаление ключа.

## Квоты Google

- **Indexing API** — по умолчанию 200 уведомлений в сутки на проект. Поэтому
  плагин по умолчанию отправляет не больше 100 URL в сутки и останавливается
  при ответе 429 до следующего дня.
- **URL Inspection API** — 2000 запросов в сутки и 600 в минуту на ресурс.
  Плагин проверяет по 4 URL за тик раз в 5 минут и тоже останавливается при
  429.

Indexing API официально предназначен для вакансий (`JobPosting`) и прямых
трансляций (`BroadcastEvent`); для остальных страниц Google не гарантирует
обработку уведомления. Плагин использует его как запрос на переобход: если
нужен гарантированный результат, дополнительно обновляйте sitemap и
пользуйтесь «Проверкой URL» в Search Console.

## Экраны плагина

- **Статистика** — карточки с количеством URL (всего, непроверенные,
  не проиндексированные, в индексе, исключённые, ждут перепроверки и
  переотправки), состояние воркеров, квоты, ручной запуск проверки и отправки,
  синхронизация.
- **URL** — таблица очереди с фильтрами, поиском, постраничным выводом,
  построчной проверкой и отправкой, массовыми действиями.
- **Логи** — записи по уровням (info, warning, error, debug) с очисткой по
  сроку хранения.
- **Диагностика** — пошаговая проверка подключения: ключ, токен, ресурсы,
  права, URL Inspection API, Indexing API, схема БД, cron, локальная
  квота, теги.
- **Настройки** — параметры и справка «Как подключить».

## Обновления

Плагин обновляется штатным механизмом WordPress из репозитория
[Gnoztis/google-indexing-manager](https://github.com/Gnoztis/google-indexing-manager):
берётся максимальная версия из GitHub Release и тегов (`vX.Y.Z` и `X.Y.Z`
равнозначны), архив — zip-ассет релиза или zipball победившего источника.
Предрелизы (`-beta`) и четырёхчастные версии (`1.13.0.1`) не принимаются,
поэтому достаточно поставить тег. Установленная версия читается из шапки файла
на диске, поэтому сразу после обновления та же версия повторно не предлагается.

Проверка кэшируется на 6 часов. Если GitHub ответил ошибкой, плагин запоминает
её на 15 минут и показывает причину в строке плагина и в уведомлении на экране
«Плагины», например «проверка не удалась: 403 (лимит GitHub API)». Кнопка
«Проверить обновления» сбрасывает и кэш, и 15-минутную паузу: это явный запрос
пользователя, а не фоновая проверка.

### Токен GitHub

Анонимный доступ к GitHub API ограничен 60 запросами в час на IP-адрес
хостинга, с токеном — 5000. На общем хостинге за одним IP работают несколько
сайтов и плагинов, поэтому лимит может исчерпаться, и тогда проверка
обновлений вернёт 403.

Токен задаётся в `wp-config.php`:

```php
define( 'GIM_GITHUB_TOKEN', 'github_pat_…' );
```

или фильтром, если значение приходит из другого места:

```php
add_filter( 'gim_github_token', static fn() => 'github_pat_…' );
```

Подойдёт fine-grained personal access token с правом **Contents: Read** на
репозиторий плагина. Токен передаётся только в запросы к `api.github.com` и
`github.com`, никогда не выводится в интерфейсе и не пишется в базу: в
диагностике видно лишь, задан он или нет.

Репозиторий плагина публичный, поэтому обновления работают и без токена — он
нужен, только чтобы не упираться в лимит. Если доступ к репозиторию закроют,
токен станет обязательным: без него GitHub не отдаст ни список версий, ни архив
обновления. Это один и тот же fine-grained PAT с правом Contents: Read —
отдельного токена для скачивания не нужно.

Токен обновлений и ключ сервисного аккаунта — разные секреты и разные системы:
`GIM_GITHUB_TOKEN` живёт только в `wp-config.php` и даёт доступ к GitHub, а
JSON-ключ сервисного аккаунта хранится в базе зашифрованным, и его защищает
константа `GIM_KEY_ENCRYPTION_KEY`.

## Удаление

`uninstall.php` удаляет только данные плагина: настройки (включая шифротекст
ключа и его подсказку), счётчики и блокировки, транзиенты (access token, кэш
статистики, кэш проверки обновлений), события WP-Cron, таблицы `*_gim_log` и
`*_gim_unindexed`, пользовательские метаданные плагина. На multisite — на всех
сайтах сети.

Удаление плагина **не отзывает** ключ сервисного аккаунта в Google Cloud:
если он больше не нужен, удалите ключ в Google Cloud и уберите сервисный
аккаунт из пользователей Search Console.
